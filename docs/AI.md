# Local draft extraction

This module connects a buyer brief to a local language model. It does not create a quote, authenticate a buyer, prove human consent, or call PayPal. The model's text is an unverified proposal even when every structural check passes.

## Data and control boundaries

`createLocalExtractor()` sends at most 2,000 UTF-16 code units of brief text and the three fictional service identifiers/names to `http://127.0.0.1:11434/api/chat`. It uses the existing `qwen3.5:9b` tag, a constrained response schema, no tools, `stream: false` and `think: false`. Prices, catalog limits, credentials and payment capabilities are not supplied by the application. A buyer could mention those strings in a brief; that does not grant authority.

The adapter accepts only the expected completed model response and a bounded JSON body. It performs one request at a time per extractor instance, with a 90-second deadline, a 64 KiB response cap, no redirects and no automatic retry. The current native HTTP server shares one extractor and additionally serializes AI operations across its anonymous workspaces, with request/session/body limits. The adapter does not expose Ollama to the network; the application listener is IPv4 loopback only. See [HTTP boundaries](HTTP.md).

Each model proposal includes an exact original-text quotation. Trusted code finds its unique occurrence and computes JavaScript UTF-16 offsets. Missing, ambiguous and overlapping repeated matches are rejected. Quotes are not translated, normalized or silently repaired. `validateAiDraft` then checks field types, bounds, duplicate fields and allowed keys. A quotation establishes where text occurred; it cannot establish that the model understood it correctly.

The suggested SKU is an unverified mapping from a service phrase, not an accepted purchase. Unknown or missing SKU means the offer has not been compared; an empty conflict array alone never means the draft fits an offer. The domain computes quantity, revision, language, format, timing, rights and publication conflicts using its own catalog. Missing fields stay unresolved independently of the model's follow-up questions.

## From extraction to a quote

Pass `result.draft` to `ScopeBook.createDraft(owner, originalBrief, result.draft)`. Keep the original brief unchanged. Present the proposals, source quotations, deterministic missing fields, comparison status and conflicts for review. Every correction and original conflict needs an explicit review record. Only a complete reviewed scope can produce a fixed catalog price.

`ScopeBook` is an in-memory domain component. The HTTP controller supplies ownership from its anonymous server-side session and enforces Origin/Host/CSRF checks. The three-language workbench presents explicit review and separate quote controls; model output cannot supply their confirmation flags. The [Sandbox payment service](PAYMENTS.md) is integrated separately and keeps durable operation records. Cookie possession and caller-supplied booleans do not prove identity, understanding or media rights. A successful model response never proves payment.

## Verification and model provenance

`npm test` runs non-inference tests. The adapter tests use fake HTTP responses for malformed or oversized content, timeouts, concurrency, field-type coercion, evidence ambiguity and forbidden price/approval fields. The server tests use actual loopback HTTP with injected fake extractors. Neither measures language-model quality or contacts PayPal.

`node tools/ai-probe.mjs` is an explicit separate local inference probe. It first reads the installed tag metadata and reported license, requires a local GGUF model, then runs owner-authored synthetic briefs sequentially. It creates a dated private receipt, records observed model/source hashes, preserves failed outcomes and checks for changes after the run. It never downloads a model or invokes PayPal. Do not run it on real account or payment data.

The historical first three-case run extracted English requested quantities and publication prohibitions, but omitted every suggested SKU and one Chinese source-readiness fact. Without a SKU, two offer-specific conflicts were not yet compared. This led to a prompt change distinguishing service-intent suggestions from accepted offers and requiring a field-by-field scan. These are observations of that earlier source/model snapshot.

The revised prompt was tested on those three briefs and a fourth synthetic caption-file brief. All four outcomes still had semantic gaps; this was not a passing quality evaluation.

| Synthetic brief | Observed gap after the prompt change |
| --- | --- |
| English clip request | SKU omitted; quantity and revision conflicts could not yet be compared. A follow-up asked about thumbnail style despite the clip request. |
| Chinese thumbnail request | SKU omitted. Source readiness was now extracted correctly, but the delivery-start condition was newly omitted. |
| Brief containing quoted malicious price/approval instructions | SKU omitted. The output did not contain price, approval or payment-success claims in this case. This one observation does not establish general injection resistance. |
| Caption-file request | SKU and the excess-revision conflict were correctly identified, but the explicit English caption language was omitted. The model asked again about language and asked about an aspect ratio that the offer does not use. |

Three of four revised-run drafts omitted the SKU. The current review workbench lists deterministic missing fields independently of model questions, allows manual completion and corrections, and compares the working scope after SKU selection. A completed extraction must not be advertised as a complete scope or an approved quote. These partial receipts remain unchanged; a later separate HTTP integration run does not replace them.

### 1 November regression and rejected candidate

A fresh run of those same four known synthetic cases on 1 November 2026 reproduced all four failures in the current adapter. It again omitted three service suggestions, the Chinese delivery-start condition and the English caption language. These are regression cases, not an unseen evaluation set.

Two bounded candidate runs then tested a fixed, field-typed slot format with exact quotations and explicit nulls for unknown facts. The first candidate matched all expected fields and conflicts in one of four cases; the second recovered every expected non-SKU field but omitted the SKU in all four cases. Both still produced some irrelevant follow-up questions. Neither candidate met the four-case acceptance condition. The candidate adapter and its tests were therefore not adopted; the existing adapter remains in place, and the omissions remain unresolved. The private receipts retain each failed outcome and source/model hashes.

The probe now additionally rejects unexpected proposal fields rather than checking only that expected values are present. Each of the twelve inference attempts in this bounded investigation used the existing local model once, without retries, downloads, new packages, PayPal calls, quotes or external publication. No broader extraction-quality improvement or production fix is claimed.

### Source-located service suggestions, 1 November

The service part of the HTTP AI path composes the unchanged local model adapter with a separate, server-owned `catalog-alias-2026-11-01-v2` rule profile. This profile covers all three current catalog services with explicit English, Traditional Chinese and Japanese aliases, including mixed-language requests. It can supply an **unverified service suggestion** when a clear request names exactly one supported service; the service helper does not extract or default other scope facts. Direct adapter consumers can use `withCatalogIntent` for this service-only behavior. The current HTTP path and probe use the additional two-field composition described below.

The rule locates a unique exact request clause in the unchanged brief and runs the existing UTF-16 evidence validator. Its provenance is returned as `extraction.serviceIntent.source: catalog_alias_rules`, with catalog/rule versions and the human-review requirement. The server constructs this metadata itself; caller metadata is rejected and extractor metadata cannot assert acceptance. The workbench labels the combined model/service suggestions as unverified. An exact quotation proves location, not semantic truth or buyer consent.

Quoted/code text, negated or conditional requests, unknown service IDs, ambiguous/narrative wording and multiple services lead to an explained manual-selection question in English, Traditional Chinese or Japanese. A valid model SKU that disagrees with a clear alias is also suppressed and explicitly reported as `model_conflict`; it is not counted as a successful service resolution. Other source-backed model fields remain unchanged. The existing service selector and complete manual-entry path remain available. The selected service still needs an explicit attribution decision, every final scope field and independent review before any quote; no quote or payment is created by this helper.

The profile is a finite rule system, not general natural-language understanding. It deliberately abstains on bare “clips”, “captions” and “files”, repeats without a unique quotation, unsupported request grammar and some unrelated conditions. More complex negation, new synonyms, languages outside this profile or a changed catalog can require manual selection or an explicit new version. The 83 owner-authored rule/domain checks exercise supported aliases, mixed language, source offsets, quotation, negation, conditions, unknown/multiple services, model disagreement and the unchanged review boundary. They are development checks rather than an unseen semantic benchmark.

Four new loopback HTTP cases verify omitted-service recovery without automatic approval, conflicting model-SKU suppression with manual review still available, rejection of caller evidence/provenance while explicit manual mode runs no inference, and suppression of another speaker or withdrawn requests while manual review remains available. The full offline suite passed 213 checks without model or PayPal calls.

Before the independent review fixes below, one bounded run of profile v1 used the existing installed model exactly once on each of the four **known regression cases**, with no prompt changes or retries. Service suggestions improved from 1/4 to 4/4, matching expected values from 28/33 to 31/33, and complete cases from 0/4 to 2/4. All four exact deterministic conflict sets matched, with no unexpected proposal fields. The same two non-service omissions remained: the Chinese thumbnail delivery-start condition and the caption-file request's explicit English language. Irrelevant model follow-up questions also remained. The strict four-case gate therefore still failed; the new behavior is a bounded service-suggestion improvement, not a complete extraction-quality pass. Source/model hashes were unchanged during this run, and the adapter hash matched the reproduced baseline. Old failures and rejected-candidate receipts remain intact.

Independent review then found false service suggestions in cross-line examples/speaker attribution, source-material references, unapproved conditions, cancellation and alternatives including unsupported services. Profile v2 adds conservative abstention for those concrete boundaries, Chinese negation and Japanese conditions/cancellation, standard tilde-fenced code and price inquiries. Twenty-three additional development cases reproduce those categories in the supported languages. Version v2 passed the full 213-check offline suite and the HTTP review boundary; it has **not** had another real-model run. The v1 model receipt and hashes are retained as v1 evidence, not attributed to the revised v2 source. These fixes concern service attribution; no payment authority was granted by either version.

The revised profile uses a narrow direct-service-object grammar rather than inferring intent from an alias anywhere in a sentence. Around the service name, it admits only explicit request verbs, finite number/language modifiers and a few count/revision/caption/aspect-ratio phrases. Unknown textual paragraphs before the request, unknown surrounding wording and negative action commands other than the demonstrated publication prohibition require manual selection. This intentionally sends some genuine requests to manual review, including briefs with facts before the service request, longer descriptions, complex phrasing or unsupported quantities. The supported examples do not establish a general speaker-attribution or natural-language parser.

### Literal caption-language and delivery-anchor proposals

The HTTP AI path and optional inference probe now use `withSourceFacts`, composing the unchanged v2 service rule with `literal-scope-facts-2026-11-01-v1`. This small profile addresses only `captionsLanguage` and `deliveryStarts`; it does not change the model prompt, schema, catalog or review requirements. Metadata is constructed on the server as `extraction.sourceFacts`, with per-field status, reason, model suppression/conflict and the rule version. The original model output and any caller/extractor metadata cannot establish these facts. A supported same-value model proposal is rebuilt from the rule's own source span; a conflicting value is removed and explicitly explained as a manual choice. Unrecognized source wording remains unresolved rather than being filled from catalog defaults.

Caption language must directly modify a caption/subtitle/file in the v2-accepted service request. The finite English, Traditional Chinese and Japanese language names map to English, Chinese, Japanese or Traditional Chinese; an unsupported catalog language remains visible as a catalog conflict. A source video's language, an English highlight video or thumbnail text does not establish caption language. Multiple language candidates or later caption/language changes require manual selection.

Delivery anchors require a complete literal timing clause: supported forms include `Delivery starts after source receipt`, `Deliver N days after receipt of usable source material`, `交期是收到素材後N天`, and `納期は素材受領後N日です`. Explicit `Delivery starts today`, `交期從今天起算` and `納期は今日から起算します` propose `calendar_now`, exposing the existing catalog-anchor conflict. No anchor is inferred from source readiness, a duration alone or a historical mention. This profile does not extract the duration or assert that the source has arrived.

Both fields also require a fully recognized surrounding frame after the direct service request: only the supported complete timing clauses and finite declarations of revision count, source readiness/source language, music rights or publication prohibition are admitted. Question-mark timing clauses, unknown text, speaker/header changes, old-contract explanations, retroactive “only an example” context, negation or conditional alternatives send the fields to manual review. Quotes, code and even apostrophes/contractions also conservatively abstain in this profile. Unknown timing history can therefore leave an otherwise explicit caption language manual too. This is deliberately limited grammar, not a general parser; the existing manual fields remain available. Every proposed value still requires an explicit attribution decision and complete independent review before a quote.

The four saved, cleared synthetic inputs and original adapter outputs are retained as a public **offline projection fixture**. Applying the v2 service rule and literal fact profile to those saved outputs matches all 33 expected values and all four exact conflict sets without unexpected fields. The original saved outputs matched 28/33, and the service-only projection matched 31/33. This is deterministic reuse of known development cases, **not a new model run, unseen evaluation, quality benchmark or evidence that the model's omissions or irrelevant questions were fixed**. The full offline suite passed 260 checks, including 45 literal-rule/domain/projection checks and two new HTTP checks for server-owned evidence, conflict suppression and explicit review decisions. This verification ran no model inference or provider call. Source publication does not deploy or validate a running application.

## One-shot HTTP integration evidence

On 2026-10-30, a separate end-to-end HTTP probe used one different, simpler cleared synthetic caption brief with the actual local adapter and model. It made exactly one `/api/chat` request, without retry or model download. The AI HTTP request completed in 18.833 seconds and returned all nine expected proposals, with no unexpected or mismatched proposal fields and valid exact UTF-16 quotation spans. `secondsPerDeliverable` and `aspectRatio` remained missing and required explicit manual `null` choices; the model returned two follow-up questions. The result remained `unverified_draft`, required human review and created no quote.

That historical run also passed 63 HTTP checks for the then-current public surface, session/CSRF boundaries and an explicitly selected manual scope-to-quote/Clear exercise. Review flags were caller assertions, not evidence of human understanding. The owned loopback server was closed afterward. `tools/flow-probe.mjs` prints a plan by default and requires `--run-once` for those operations. Public setup and verification do not require private development receipts.

One simpler synthetic success is not a representative model-quality pass, a regression rerun of the earlier four cases, evidence that their omissions are fixed, or a browser/UI/PayPal/deployment validation. Source changes after the recorded hashes need their own appropriate verification; do not attribute later race fixes to this run.

The tested installed tag reported GGUF/Q4_K_M and an Apache 2.0 license. This is an observation about that installed artifact, not a promise that a later mutable tag contains identical bytes. No weights are bundled. Use the linked model source/license, inspect your installed tag and validate its actual behavior. Model changes require a new provenance and quality check; a clean local clone passed offline tests, but clean judge-machine model installation and inference have not been performed.

The model returned nine proposals and left two scope fields for manual completion. English, Traditional Chinese and Japanese desktop views were checked separately. The full **126-case** offline suite does not run the model or PayPal. See [EVIDENCE.md](EVIDENCE.md) for the bounded public summary and [JUDGING.md](JUDGING.md) for free local setup.

A third, distinct Sandbox flow then used a new 217-character synthetic brief and **one** real local `qwen3.5:9b` request. It produced **seven** proposals, **four** deterministic missing fields and **zero original catalog flags**. The operator individually accepted the seven proposals after review and manually completed the four missing fields, reaching all eleven final fields before the fixed USD 35 quote and separate payment actions. The zero flag count did not resolve the missing values. This is another observed simple caption case, not a replay of the earlier nine-proposal flow or a rerun of the four-case semantic evaluation. The completed state was viewed in the three interface languages; that is not evidence that briefs in all three languages were extracted accurately.

Use only cleared synthetic briefs. No account/payment data, private runtime journal or credentials belong in model input or a public release. Real Sandbox execution and successful simple extractions do not resolve the historical four-case omissions, establish representative multilingual extraction quality, or prove all mobile/accessibility states. Remote AI, clean-machine model/account setup and production readiness are not claimed.
